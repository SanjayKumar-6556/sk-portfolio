## In one line

An English-narrated video goes in; a single MP4 comes out with the original audio plus a
synthesised dub in each requested language, selectable in any normal player.

**Skills demonstrated:** multi-stage media pipeline design, speech and LLM API orchestration,
checkpointing and resumability, cost-aware batching, concurrency, packaging for delivery.

## Context

Built during my AI/ML internship at Wow Labz (May–November 2024). The brief was localisation of
narrated video: the same content had to reach audiences in several Indian languages without
re-recording it each time.

The constraints that shaped every design decision were cost and failure. Cloud transcription,
translation and speech synthesis are billed per unit of text or audio, and a long video is a
long sequence of billable calls. A naive script that crashes on stage five and restarts from
stage one pays for stages one through four a second time.

## My role

I designed and built the pipeline: the stage decomposition, the resumable runner, the chunking
strategy, the muxing, and the Streamlit interface over it. A frontend for end users was never
built — the deliverable was the backend pipeline and an operator-facing UI.

## Architecture

```text
 video ──► extract audio ──► transcribe ──► sentence split ──► chunk
                              (Whisper)       (spaCy)      (≤4900 bytes)
                                                                │
                        ┌───────────────────────────────────────┤ per language
                        ▼                                       ▼
                  translate (GPT-4o,                      synthesise speech
                  gender-aware prompt)                    (Google Cloud TTS)
                        └───────────────────────────────────────┘
                                                                │
                                                                ▼
                                          mux all tracks into one MP4 (ffmpeg)
                                          + optional 360p/720p transcode, DASH/HLS
```

**Sentence-aware chunking.** Text is split on sentence boundaries with a per-language spaCy
sentencizer, then packed into chunks of at most 4,900 bytes — just under the Google TTS
per-request limit. Splitting on bytes alone would cut mid-sentence and produce translations that
drift; splitting on sentences alone would overflow the request limit. The packer does both.

**Resumable execution.** The tracked variant of the pipeline persists each stage's artefacts to
disk — chunked text, then audio byte chunks — keyed so that a rerun skips anything already
completed. An interrupted run resumes instead of re-translating and re-synthesising work that
was already paid for. Each stage fans out across languages through a thread pool.

**Rhythm preservation.** A pause-detection step finds silences in the source audio and emits
SSML break tags into the synthesis input, so the dubbed speech keeps something of the original
speaker's pacing instead of running as an unbroken block.

**Delivery.** The muxing step maps the original English track plus every synthesised track into
one container with per-track titles. A transcoding step can additionally emit multiple
resolutions and package for adaptive streaming.

## Trade-offs

- **Whisper-small, not large.** The small model was chosen for turnaround; the model name is a
  single configuration value, so upgrading it is a config change rather than a rewrite. Accuracy
  was traded for iteration speed at a point where the pipeline shape was still moving.
- **LLM translation rather than a translation API.** A plain translation endpoint is cheaper and
  faster, and the codebase keeps one as an alternate backend. GPT-4o was used for the main path
  because the prompt can carry instructions a translation endpoint cannot — notably grammatical
  gender agreement with the chosen voice, which the Indian languages in scope need and a generic
  translation call gets wrong.
- **Checkpoints on disk, not a queue or database.** For a pipeline that runs per video on one
  machine, files on disk gave resumability at almost no operational cost. It does not generalise
  to a distributed fleet, and that limit was accepted deliberately.

## Honest limitations

Documented in the repository rather than glossed over: translated speech drifts in length from
the original, so SSML pause insertion mitigates but does not solve lip-sync; cloud TTS and
translation are billed per character; adaptive-streaming packaging depends on an external
packager binary.

## What I would do differently

- **Ship a demo artefact with the pipeline.** There is no sample video, no side-by-side audio
  clip, nothing a reviewer can listen to. For a system whose entire output is perceptual, that
  is the single biggest gap, and it would have cost an afternoon.
- **Make quality measurable.** The pipeline has no automated check on translation or synthesis
  quality — no back-translation comparison, no duration-drift metric per chunk. Those are cheap
  signals and they would have caught problems that only surfaced on listening.
